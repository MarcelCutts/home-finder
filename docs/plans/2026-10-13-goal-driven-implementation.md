## Research and operating method

Official guidance describes a goal as a persistent thread objective with a verifiable finish condition. It should name an outcome, constraints and evidence, rather than simply ask for continual improvement. Goal state remains active until the outcome is supported or a real stopping condition applies; a test failure is a reason to repair or investigate. [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex).

An open-ended backlog is too broad for one useful completion condition. Use consecutive goals for related outcomes, each with checkpoints and a short progress record. [Follow a goal](https://learn.chatgpt.com/docs/use-cases/follow-goals). The older execution-plan recipe also supports retaining decisions, reproducible commands and independently verifiable milestones; it is archived, so its model recommendations are not being adopted. [Execution plans](https://developers.openai.com/cookbook/articles/codex_exec_plans).

For this repository, implementation proceeds through one small behaviour change, a meaningful regression scenario, focused checks, and a recorded result. At milestone boundaries, broaden validation only as warranted by the changes. Keep the existing money, source-identity, transaction and delivery protections. Document external prerequisites separately from offline acceptance. Do not mark a deployment or real-provider experiment verified because mocks pass.

Only one native goal is active at a time. Later goals below are a queue, not simultaneous goals or extra agents. No token budget was requested or set. The user can steer or pause the active goal; unfinished work remains explicitly unfinished.
